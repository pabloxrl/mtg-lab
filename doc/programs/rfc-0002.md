# RFC 0002 implementation program

The [MVP parent issue](https://github.com/pabloxrl/mtg-lab/issues/7) is the live
progress record. This program preserves the complete [MVP RFC](../rfcs/0002-first-mvp.md)
under the [project charter](../rfcs/0001-project-charter.md). M0 is complete. Operations [#59](https://github.com/pabloxrl/mtg-lab/issues/59)
authorizes the existing M1–M5 delivery commitments under the standing full-program
mandate. Authorization is not implementation or permission to skip a preceding
stage gate. Successful gates hand off to the next eligible task automatically.

## Acceptance coverage

- [Requirement inventory](rfc-0002-requirements.json) preserves every section,
  table, example and constraint verbatim, including source lines and owner issues.
- [Program manifest](rfc-0002.json) defines task order, dependencies, milestone
  gates and current execution authorization.
- `python3 scripts/check_program.py` verifies lossless coverage, source pins,
  bidirectional ownership, an acyclic dependency graph and milestone prerequisites.
  It reads files and Git objects only; it does not dispatch work.
- `./scripts/verify.sh` runs that check and its negative tests in required CI.

The 44 source blocks are coverage groups, not 44 individual requirements. All
clauses within each block remain mandatory where applicable. Shared ownership
means each stage must deliver its assigned aspects; closing one owner does not
satisfy the entire block. Source changes require deliberate RFC/ledger review,
not automatic regeneration that silently blesses a reduced requirement.

No milestone is done because all its children are closed. Its gate must rerun
acceptance checks and deliver an independently reviewed report for an exact main
commit, with commands, versions, artifact links/digests and unresolved limitations.
The existing synthetic comparator is groundwork, not M0 or game conformance.

## How execution advances

After operations #59 passes review and exact-main CI, the coordinator queues
#17 to resume M1. Later successful milestone gates use the same bounded handoff. One Symphony implementation worker runs at a time.
A task follows implementation, checks, separate review, protected auto-merge and
exact-main CI. It records evidence on itself and the parent, then labels at most
one eligible registered successor before atomically closing itself.

A failed dependency prevents downstream execution. Independent ready work may
continue. A dependency needs verified completion evidence, not merely a closed
state. The M0 gate cannot run until all seven M0 implementation tasks pass; later
milestones require their preceding gate. All currently registered stages are
already authorized by #59; no separate routine activation is needed at each gate.
Workers do not change the task registry or expand their own authorization.

This is agent-managed handoff using existing Symphony/GitHub, not a new scheduler.
Ordinary handoff retries retain the current issue and reuse the queued successor.
Abrupt shutdown, forced closure, exhausted dispatch budget or an API failure can
still require the coordinator to reconcile the queue. See the
[operator runbook](../symphony-runbook.md) for commands and recovery.

## Your role and controls

Read the parent workpad for delivered capabilities, evidence, blockers and the
next task. Comment there to steer product direction; no routine plan or PR
approval is required. Agents handle implementation decisions and queue progression.

Add `program-paused` to the parent to stop program work at the next checkpoint;
`program-cancelled` withdraws execution authorization. Add `agent-held` to a child
to hold it. Stop the local service for immediate shutdown. A held/previously
paused issue requires explicit coordinator reactivation; successor selection
never silently undoes that choice.

Two later prerequisites remain visible: the owner must choose a repository
license before release publication, and performance qualification needs access
to the RFC's designated Linux hardware. M0 can record a conservative distribution
policy without inventing either decision. Missing reference builds, rights,
access, or acceptance evidence never count as passing checks.

## Docker execution prerequisite

Operations issue #47 is an additional M0 prerequisite, with its own operational
acceptance criteria and no reassignment or deletion of RFC requirements. The
manifest's `execution` contract identifies Docker and gates #13–#16 on #47;
subsequent milestones remain downstream of M0. The validator rejects bypassing
these edges. Previously completed M0 deliveries retain their evidence.

During migration parent #7 is `program-paused`, #13 is held, and the native
controller is stopped. The coordinator preserves #13's workspace, builds and
reviews the container runtime, proves authentication/sandbox/verification and a
real Linux XMage smoke run, then verifies restart recovery. Only after the
operations completion report and successful exact-main CI may #47 close and the
coordinator clear the parent pause and explicitly reactivate #13. A failed
migration keeps the program paused; it never silently falls back to host builds.
The XMage candidate remains unaccepted until its own #13 review and delivery.

The operator continues describing work through GitHub issues. Start/stop/status
commands are in the [Docker runbook](../symphony-runbook.md). Changes to the image
or deployment need an operations issue; workers cannot install host tooling.

The [MVP test strategy](../testing/README.md) and its component plans refine existing
acceptance without changing the pinned RFC. Correction #52 supplies concrete
positive/negative/interaction/regression designs for every scoped capability.
Operations #54 registers that correction; #16 must re-audit after both deliveries.

separate. Later-stage owners must implement the linked test plans alongside their
